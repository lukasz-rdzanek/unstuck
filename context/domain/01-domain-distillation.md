# Unstuck — Domain Distillation

> A domain **map**, not code. Read-only distillation from source documents and
> verified source files. Every concept is cited to `file:line` that was actually
> opened; gaps are marked **"unknown"** or **"MISSING in code"** rather than
> guessed. Steps follow the DDD distillation order: discovery → ubiquitous
> language → subdomain classification → aggregates/invariants → model-vs-code
> divergence → refactor ranking.

---

## STEP 0 — Project context (discovery)

- **Product (PRD):** A learning platform whose distinct bet is **lesson-scoped chat** — peer help attached to the exact lesson, surfaced where the learner is already working. `context/foundation/prd.md:20-24` (Vision), `:32-44` (Success Criteria). The MVP loop is: land on a lesson → hit a blocker → post in the lesson chat → find an operator-seeded or peer answer → resume. `prd.md:36`.
- **Stack:** Astro 6 SSR + React 19 islands, Tailwind 4, Supabase (auth + Postgres + Realtime), deployed to Cloudflare Workers. `AGENTS.md` (Architecture), `context/map/repo-map.md:11-24`.
- **Where business logic lives:** `src/lib/services/*` (DI services), `src/lib/srs.ts` (FSRS scheduling), `src/pages/api/**` (grading/scheduling endpoints), and — critically — **Postgres SECURITY DEFINER functions** in `supabase/migrations/**` (grading, access predicate, semantic match). The import graph cannot see RLS/RPC/Realtime coupling (`repo-map.md:89-108`), so the migrations are first-class domain sources here, not infrastructure detail.
- **The headline discovery (drives the whole document):** the PRD and roadmap describe a **lesson-chat MVP** and explicitly list completion tracking and recommendation engines as **Non-Goals** (`prd.md:127,131`). The codebase has since grown a whole second domain — **a learning/assessment loop** (tests, spaced-repetition, AI answer matching, completion) shipped under roadmap "BETA COMPLETE / UNS-24" (`roadmap.md:15-24`). The governing PRD (v1) was **never updated** to describe these. Most divergences below trace to this: **the code's domain has outgrown its written domain.**

### 1d. Identified one-concept-many-names drift (the "3xAccount" hunt)

- **DRIFT-1 — Message:** `messages` (table) → `Message` (row type) → `LessonChatMessage` (view type with author, embedding omitted, `types.ts:77-79`) → `NewMessage` (insert DTO, `types.ts:65`). This is _layered DTO derivation_, which `AGENTS.md`/`types.ts:10-15` sanctions — **benign**, not harmful drift.
- **DRIFT-2 — Test vs Quiz:** the same entity is "test" in the table/route/service and "quiz" in comments and the UI island `TestQuiz.tsx`. Source: header `tests.ts:1` ("tests/quizzes"), `tests_schema.sql:5` ("Tests (quiz)"). **Harmful-ish**: a reader cannot tell from the word "quiz" whether a third concept exists. Low cost to fix (vocabulary note).
- **DRIFT-3 — the SRS Card (the real "3xAccount"):** ONE concept — a per-user FSRS scheduling card — appears as **four+ names across layers**: `Card`/`SrsCardFields` (`srs.ts`), `srs_review_state` + `srs_question_state` (tables), "review" vs "practice" (routes/UI), and a hand-copied `CARD_COLUMNS` string in three route files. The lesson-level and question-level cards are _structurally identical_ (same 9 FSRS columns, `srs_question_state` migration `:14` literally says "mirror of srs_review_state") yet share no type or module. **This is the canonical drift finding** — confirmed independently by `context/changes/practice-srs-grading-analysis/research.md` (Summary).

### #1, named and justified

**Decide and act on the lesson-level review feature (`srs_review_state` + `review_enabled` enrolment).** It is #1 because it sits at the intersection of the highest value and the highest risk in the matrix: the invariant INV-8 is the only one classified **ignored** (a rule the schema _declares_ but no code path enforces — `complete.ts` never reads `review_enabled`), and the feature it belongs to is **orphaned** (a tested API + table with no UI entry point, DIV-3). Every future reader of `srs_author_config.sql` will believe completing a lesson enrols it for review; it does not. The fix is a fork in the road, not a tweak — **wire it** (add the enrolment write to `complete.ts` behind `review_enabled`, plus a due-review queue UI mirroring the working practice flow) **or remove it** (drop the orphaned columns/table/endpoint). Either resolves the divergence; leaving it is the costliest option because the code actively lies about a domain rule.
